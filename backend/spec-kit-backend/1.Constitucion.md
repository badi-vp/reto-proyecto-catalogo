# Constitución del backend del catálogo de motos

## 1. Objetivo

Construir una API REST para administrar el catálogo de motos de `catalogoMotos`.
El backend permitirá autenticar al administrador, gestionar motos y consultar el
catálogo mediante filtros.

## 2. Tecnologías

### Lenguaje y runtime

- **TypeScript** como lenguaje principal.
- **Node.js Runtime** para desarrollo y producción.
- No se utilizará Edge Runtime porque el proyecto utiliza PostgreSQL y bcrypt.

### Capa HTTP

- **Hono.js** para construir la API REST.
- **@hono/zod-validator** para integrar validaciones Zod en las rutas.
- Middleware de Hono para autenticación, CORS, logs y manejo de errores.

### Autenticación y seguridad

- **JWT** para representar la sesión autenticada.
- El JWT se devolverá en JSON y el frontend lo almacenará en `localStorage`.
- Las rutas protegidas recibirán el JWT mediante `Authorization: Bearer <token>`.
- **bcrypt** para proteger las contraseñas.
- El factor de trabajo de bcrypt será de **8 saltos**.

```ts
bcrypt.hash(password, 8)
```

### Validación

- **Zod** para validar cuerpos de solicitudes, parámetros de ruta, filtros y
  variables de entorno.

### Base de datos

- **PostgreSQL**.
- El esquema existente se encuentra en la carpeta `db` y utiliza sintaxis de
  PostgreSQL.
- **pg** será el cliente de conexión desde Node.js.
- Las consultas deberán utilizar parámetros y nunca concatenar directamente
  valores proporcionados por el usuario.

## 3. Compatibilidad con Vercel

Hono dispone de integración oficial con Vercel sin configuración compleja.
La aplicación deberá exportarse como `default` desde un archivo reconocido por
Vercel, preferentemente `src/index.ts`.

```ts
import { Hono } from 'hono'

const app = new Hono()

export default app
```

Consideraciones:

- Las rutas de Hono se ejecutarán como Vercel Functions.
- El desarrollo local se realizará con `vc dev`.
- La aplicación se desplegará con Vercel usando Node.js Runtime.
- `serveStatic()` de Hono no se utilizará para servir archivos estáticos en
  Vercel; esos archivos deberán ubicarse en `public`.
- El pool de conexiones de PostgreSQL deberá reutilizarse mediante una
  instancia singleton para evitar crear conexiones innecesarias por solicitud.
- Las variables sensibles se configurarán en Vercel y no se almacenarán en el
  repositorio.

Documentación oficial:

- [Hono en Vercel](https://hono.dev/docs/getting-started/vercel)
- [Hono en Vercel - Vercel Docs](https://vercel.com/docs/frameworks/backend/hono)
- [Node.js Runtime - Vercel Docs](https://vercel.com/docs/functions/runtimes/node-js)

## 4. Arquitectura

Se utilizará una arquitectura de tres capas:

```text
Rutas / HTTP
     ↓
Controladores
     ↓
Servicios
     ↓
Repositorios
     ↓
PostgreSQL
```

### Capa HTTP y presentación

Responsabilidades:

- Definir rutas REST.
- Leer cuerpos, parámetros, query strings y headers de autorización.
- Ejecutar validaciones Zod.
- Ejecutar middleware JWT.
- Convertir resultados a respuestas HTTP.

Directorios:

```text
routes/
controllers/
middlewares/
schemas/
```

### Capa de aplicación

Responsabilidades:

- Implementar reglas de negocio.
- Autenticar administradores.
- Comparar contraseñas mediante bcrypt.
- Generar y validar JWT.
- Coordinar los repositorios.
- Gestionar errores de negocio.

Directorio:

```text
services/
```

### Capa de persistencia

Responsabilidades:

- Administrar la conexión con PostgreSQL.
- Ejecutar consultas parametrizadas.
- Consultar administradores.
- Registrar y actualizar motos.
- Listar y filtrar motos.

Directorios:

```text
repositories/
database/
```

## 7. Variables de entorno

Se deberá crear `.env.example` con la siguiente estructura:

```env
NODE_ENV=development
PORT=3000

DATABASE_URL=postgresql://postgres:password@localhost:5432/catalogomotos

JWT_SECRET=
JWT_EXPIRES_IN=1h
BCRYPT_ROUNDS=8
FRONTEND_ORIGINS=http://localhost:4321,http://127.0.0.1:4321
```

El archivo `.env` real no deberá subirse al repositorio.

## 8. Modelo de datos utilizado

### Administrador

- `Identificador`
- `Usuario`
- `Contrasena`

### Moto

- `Identificador`
- `Modelo`
- `Marca`
- `Categoria`
- `Cilindrada`
- `Precio`
- `ImagenLink`
- `Stock`
- `Descripcion`

Reglas existentes:

- El usuario admite como máximo 15 caracteres.
- La contraseña admite como máximo 60 caracteres.
- La marca permitida es `Power Motorcycle`.
- Las categorías permitidas son `Automaticas`, `Aventura`, `Deportiva`,
  `Scoter` y `utilitarias`.

## 9. Requisito de seguridad para la contraseña

La contraseña del administrador nunca deberá persistirse en texto plano en la
implementación final. La contraseña inicial definida para el administrador es:

```text
sabino007232
```

El seed actual inserta un hash bcrypt generado con 8 salt rounds; la contraseña
original no se persiste en la base de datos.

## 10. API REST

### Inicio de sesión

```http
POST /api/auth/login
```

Solicitud:

```json
{
  "usuario": "sabino007",
  "contrasena": "sabino007232"
}
```

Proceso:

1. Validar la solicitud con Zod.
2. Buscar el administrador por usuario.
3. Comparar la contraseña con bcrypt.
4. Generar el JWT.
5. Devolver el JWT en JSON para que el frontend lo almacene en `localStorage`.
6. Devolver una respuesta sin incluir la contraseña.

Respuesta esperada:

```json
{
  "mensaje": "Inicio de sesión exitoso",
  "usuario": "sabino007"
}
```

### Cerrar sesión

```http
POST /api/auth/logout
```

La operación deberá confirmar el cierre de sesión. El frontend eliminará el JWT
de `localStorage`.

### Registrar una moto

```http
POST /api/motos
```

Requiere autenticación JWT.

### Actualizar una moto

```http
PUT /api/motos/:identificador
```

Requiere autenticación JWT y deberá devolver `404` cuando el registro no exista.

### Listar motos

```http
GET /api/motos
```

Devuelve las motos disponibles.

### Filtrar motos

```http
GET /api/motos?categoria=Aventura&modelo=BROZZ&precioMin=10000&precioMax=30000
```

Filtros previstos:

- `modelo`
- `marca`
- `categoria`
- `cilindrada`
- `precioMin`
- `precioMax`
- `stockDisponible`

El listado y el filtrado se resolverán mediante el mismo endpoint con parámetros
opcionales.

## 11. Reglas de negocio

- Solo un administrador autenticado puede registrar motos.
- Solo un administrador autenticado puede actualizar motos.
- Las contraseñas nunca se devolverán en las respuestas.
- Todas las consultas SQL serán parametrizadas.
- La marca solo puede ser `Power Motorcycle`.
- La categoría debe pertenecer al conjunto permitido por la base de datos.
- El stock, precio y cilindrada no pueden ser negativos.
- Los errores internos no deberán exponer credenciales ni detalles sensibles.

## 12. Formato de errores

Todas las capas deberán utilizar respuestas de error consistentes:

```json
{
  "error": {
    "codigo": "VALIDATION_ERROR",
    "mensaje": "Los datos enviados no son válidos",
    "detalles": []
  }
}
```

Códigos HTTP previstos:

- `200 OK`: operación exitosa.
- `201 Created`: recurso creado.
- `400 Bad Request`: datos inválidos.
- `401 Unauthorized`: autenticación requerida o incorrecta.
- `404 Not Found`: recurso inexistente.
- `409 Conflict`: conflicto con el estado actual.
- `500 Internal Server Error`: error no controlado.

## 13. Fases de construcción

### Fase 1: Constitución del proyecto

- Crear el proyecto Node.js.
- Configurar TypeScript.
- Instalar Hono y sus dependencias.
- Crear `src/index.ts` y `src/app.ts`.
- Crear scripts de desarrollo, prueba y producción.
- Confirmar que la aplicación inicia correctamente.

### Fase 2: Integración con Vercel

- Configurar el punto de entrada compatible con Vercel.
- Exportar la aplicación Hono como `default`.
- Verificar el proyecto con `vc dev`.
- Crear `vercel.json` solo si la configuración predeterminada no fuera suficiente.
- Probar el despliegue de una ruta de salud.

### Fase 3: Conexión con PostgreSQL

- Instalar `pg`.
- Crear el pool de conexiones singleton.
- Leer la configuración desde variables de entorno.
- Implementar repositorios para administradores y motos.
- Probar la conexión y las consultas básicas.

### Fase 4: Validaciones

- Crear schemas Zod de autenticación.
- Crear schemas de creación y actualización de motos.
- Crear schema de filtros.
- Validar variables de entorno.
- Implementar respuestas de validación.

### Fase 5: Autenticación

- Crear `auth.service.ts`.
- Comparar contraseñas con bcrypt.
- Generar hashes usando 8 saltos.
- Generar y verificar JWT.
- Crear middleware de autenticación.
- Crear login y logout.
- Configurar el envío del JWT mediante `Authorization: Bearer`.

### Fase 6: Registro y actualización de motos

- Implementar `POST /api/motos`.
- Implementar `PUT /api/motos/:identificador`.
- Proteger ambas rutas con JWT.
- Aplicar las validaciones de negocio.
- Manejar registros inexistentes y datos inválidos.

### Fase 7: Listado y filtrado

- Implementar `GET /api/motos`.
- Agregar filtros combinables.
- Usar consultas parametrizadas.
- Definir respuesta cuando no existan resultados.
- Preparar paginación para una fase posterior.

### Fase 8: Manejo global de errores

- Crear middleware global de errores.
- Unificar respuestas.
- Controlar errores de JWT, bcrypt y PostgreSQL.
- Ocultar detalles internos en producción.
- Agregar logging controlado.

### Fase 9: Pruebas

- Probar login correcto e incorrecto.
- Probar logout.
- Probar rutas protegidas sin JWT.
- Probar registro y actualización de motos.
- Probar listado y filtros.
- Probar categorías y marca inválidas.
- Probar valores negativos.
- Probar errores de conexión.

### Fase 10: Seguridad y despliegue

- Configurar variables de entorno en Vercel.
- Configurar HTTPS y un secreto JWT seguro en producción.
- Configurar CORS para el frontend autorizado.
- Revisar consultas parametrizadas.
- Revisar que no se expongan contraseñas.
- Desplegar en Vercel.
- Ejecutar pruebas contra el entorno productivo.

## 14. Criterios de aceptación

- La API inicia correctamente en Node.js y Vercel.
- El administrador puede iniciar sesión con credenciales válidas.
- Las credenciales inválidas reciben `401`.
- El logout elimina la sesión del cliente.
- Las rutas de escritura requieren JWT.
- Se pueden registrar y actualizar motos.
- El listado permite aplicar filtros combinados.
- Las entradas inválidas reciben errores claros mediante Zod.
- Las contraseñas se almacenan únicamente mediante bcrypt.
- PostgreSQL recibe solamente consultas parametrizadas.
- El backend no expone secretos ni contraseñas.
